## PART 1 — Executive Project Summary

**Client Portal CRM** is a multi-tenant CRM SaaS application for freelancers and small agencies. Each signed-up account becomes its own **Organization** ("workspace" / tenant) with its own staff team, its own Clients/Projects/Tasks/Invoices, its own billing subscription, and — its most distinctive feature — an optional **Client Portal**: a separate, thinner login where the freelancer's *own clients* can sign in to see only their own projects and invoices.

**What it does:** lets a freelancer or small agency track clients, run projects broken into tasks, issue invoices, collaborate internally via comments/@mentions/notifications, see their business at a glance via a dashboard and analytics, manage a staff team with roles, and optionally give each client a self-service portal into their own work — all as a single coherent product, not a set of disconnected tools.

**Who it's for:** freelancers and small agencies who currently juggle a generic CRM/spreadsheet, a separate invoicing tool, and no real way to share status with clients except email.

**Major workflows already implemented:**
1. Sign up → get a personal Organization automatically → invite teammates → invite a client → track work → invoice → get paid (status tracked manually) → client sees their own portal.
2. Staff manage Clients → Projects → Tasks → Invoices, all scoped to one Organization.
3. A Client is invited to the Client Portal (separate identity) and can log in to see only their own projects/invoices.
4. An Owner/Admin manages team roles, billing plan/usage, company profile, and (for whoever operates the whole deployment) a separate Platform Admin console across all tenants.

**Overall architecture:** Next.js App Router (Server Components + Server Actions, no client-side data-fetching library), Prisma ORM against PostgreSQL (Supabase-hosted), Supabase Auth for both staff and portal identities, Supabase Storage for files, Tailwind CSS for styling, deployed to Vercel. No REST/GraphQL API layer for the app's own UI — pages read data directly via Prisma in Server Components, and all mutations go through Server Actions. A handful of real Route Handlers exist only where a Server Action can't work (Paddle webhook, file downloads, cron jobs, search-as-you-type, auth email-confirmation callback).

**Maturity assessment (evidence-based, detailed in Part 26):** this is a **functional, feature-complete MVP-to-early-SaaS-grade product**, not a prototype and not yet a fully hardened production SaaS with paying customers. It has real multi-tenant data isolation, a real (but not live-validated) payment integration, 3,130 automated tests, 15 dedicated security checks, and a clean lint/typecheck/build — but it has never processed a real transaction, never had a real customer, and carries a short, explicitly disclosed list of known gaps (custom-domain verification, invoice email delivery, cross-instance rate limiting, billing reconciliation). Staff can create/edit/delete flat or itemized `DRAFT` invoices, manage the seven allowed transitions among existing non-`DRAFT` legacy invoices, duplicate a `CANCELLED` invoice into a fresh, editable `DRAFT`, and — as of official Slice 3's sub-PR 3a/3b/3c, PR #77, and PR #79 — **Issue a `DRAFT` invoice and download its archived PDF as either staff or the connected Client Portal user, or retroactively archive an existing eligible non-DRAFT invoice that predates Issue**, which server-authoritatively recalculates its totals, builds immutable issuer/recipient snapshots, renders and archives an immutable PDF to private Storage, and — since sub-PR 3c (staff), PR #77 (Portal), and PR #79 (Legacy Archive) — serves that same immutable PDF back to any authenticated staff member or the invoice's own Client Portal user via a short-lived signed URL — all implemented end to end, and — as of PR #82/PR #83 — a bounded, claim-token-based worker now automatically reconciles any orphaned archive object on a once-daily production schedule, with a successful first automatic execution already observed. Official Slice 1 and Slice 2 are complete; **official Slice 3 (the combined Issue/finalization, PDF-archival, Legacy Archive, and bounded archival reconciliation/cleanup slice) is now complete** — sub-PR 3a (PDF rendering foundation), sub-PR 3b (the live Issue operation), sub-PR 3c (staff signed PDF download/view), PR #77 (Portal invoice PDF access), PR #79 (Legacy Archive), and PR #82/PR #83 (bounded archival reconciliation/cleanup, implemented and activated) have all shipped — see Part 11.

## PART 3 — Current Application Architecture

**Frontend:** Next.js 16.2.12 App Router, React 19.2.4, TypeScript, Tailwind CSS 4. No client-side data-fetching library (no SWR/React Query/Apollo) — pages fetch data server-side. A small set of Client Components exist only where real interactivity is needed (forms, dropdowns, the comment mention combobox, search-as-you-type).

**Backend/server:** Server Components read data directly via Prisma. Mutations go through **Server Actions** (`"use server"` files, typically named `actions.ts` next to each route) — this is the dominant pattern throughout the app, not a REST API. A small number of real Route Handlers exist under `src/app/api/` for cases Server Actions can't cover: `POST /api/billing/webhook` (Paddle), `GET /api/attachments/[id]/download` and `GET /api/portal/attachments/[id]/download` (authenticated Route Handlers that issue a short-lived signed Supabase Storage URL and return a 307 redirect to it — they never stream/proxy file bytes through Next.js), `GET /api/search` (search-as-you-type), `GET/POST /api/cron/notification-delivery` and `/api/cron/notification-cleanup` (Vercel Cron), `GET /api/cron/invoice-pdf-reconciliation` and its unscheduled `/dry-run` sibling (Vercel Cron, activated PR #83 — see Part 11), plus `src/app/auth/confirm/route.ts` (Supabase email-confirmation callback).

**Testing:** Vitest (unit + integration) and Playwright (E2E) — see Part 21.

## PART 5 — Authentication

Two fully separate, fully implemented authentication systems exist, both on Supabase Auth:

**Staff auth** (`src/app/(auth)/`, `src/lib/supabase/server.ts`, `src/lib/current-user.ts`):
- Signup (`/signup`) — public self-serve, creates a Supabase Auth user; `getOrCreateUser()`/`getOrCreateOrganizationId()` lazily provision the Prisma `User` row and a personal `Organization` (+ a `TRIALING` `Subscription`, atomically) on first real request, race-safe via a transaction + P2002-conflict fallback.
- Login (`/login`), logout, forgot-password (`/forgot-password`) → reset-password (`/reset-password`) — all implemented, all real Supabase Auth calls (`src/lib/auth/password-reset.ts`, `src/lib/auth/recovery-token.ts`).
- Email verification: handled via `src/app/auth/confirm/route.ts`, a real Supabase callback route.
- No OAuth/social login found anywhere in the codebase — email/password only.
- Session handling: Supabase's own cookie-based session, refreshed on every request by `middleware.ts`; server code always re-verifies via `getVerifiedAuthUser()` rather than trusting a cookie payload.
- Protected routes: every page under `(dashboard)` calls `getOrCreateUser()`/`getCurrentUserOrganization()` server-side; there is also a top-level guard in `(dashboard)/layout.tsx` and a defense-in-depth check inside `getOrCreateUser()` itself (a Portal-only identity can never get a staff `User`/`Organization` auto-provisioned, even via a background sidebar prefetch request).
- Redirects: unauthenticated → `/login`; a signed-in Portal identity landing on a staff page is redirected to `/portal`. `src/lib/safe-redirect.ts` sanitizes every `redirectTo` value so an open-redirect is never possible.

**Client Portal auth** (`src/app/portal/`, `src/lib/current-portal-user.ts`):
- Structurally separate signup/login/forgot-password/reset-password pages and Server Actions (`src/app/portal/login`, `/portal/signup`, `/portal/forgot-password`, `/portal/reset-password`), each targeting a `PortalUser` row rather than a staff `User`.
- Access is invitation-only: a staff member sends a `ClientInvitation`; accepting it creates the `PortalUser` row (id = the new Supabase auth user's id) — there is no open self-serve portal signup independent of an invitation.
- `getCurrentPortalUser()` is a strict, redirect-on-failure resolver used inside already-gated portal pages; `getOptionalPortalUser()` is a non-throwing variant used for identity-routing decisions. Neither ever provisions anything — a `PortalUser` row (with a `Client` that has a real `organizationId`) must already exist.

**Onboarding:** a dismissible "Getting started" checklist on the staff Dashboard, computed live from real Client/Project/Task/Membership/PortalUser data plus explicit skip/dismiss rows for the handful of steps with no data equivalent (Company Profile, Payment Details, Domain Setup, Welcome, Finish). A separate, simpler welcome banner exists on the Client Portal side.

## PART 6 — Workspaces / Multi-Tenancy / Roles

**Model:** every account is an `Organization`. A `User` joins one or more Organizations via `Membership` rows, each carrying a `Role` (`OWNER`/`ADMIN`/`MEMBER`).

**Creation:** automatic and lazy — the first time a new Supabase Auth user is resolved server-side, `getOrCreateOrganizationId()` creates a personal Organization (name from the signup form's company-name field if provided, else `"<name>'s Workspace"`), a unique slug, an `OWNER` Membership, and a `TRIALING` Subscription, all in one transaction.

**Active-organization resolution:** an httpOnly cookie (`active_organization_id`) records the user's last-chosen org as a UX preference only — it is **never trusted as an authorization decision**; every read re-verifies a live `Membership` row exists before honoring it, falling back to the user's `OWNER` org otherwise.

**Issue/finalization (`DRAFT → SENT`, sub-PR 3b, PR #73, official Slice 3 in progress):**
- The only way to move an invoice out of `DRAFT` today. Exposed on the `DRAFT` edit page only, to the **OWNER role only** (re-checked independently by both the dedicated Server Action, `src/app/(dashboard)/invoices/[id]/edit/issue-actions.ts`, and the service itself, `issueInvoice()` in `src/lib/invoices/pdf/issue-invoice.ts` — never trusting the UI hiding the control for ADMIN/MEMBER) — behind a small client-side dirty-state coordinator (`InvoiceDraftPanel`) that disables Issue with "Save changes before issuing." until the form has been saved, and a confirmation dialog (`InvoiceIssueControls`).
- On Issue: every total is recalculated server-side from the persisted line-item primitives (never a stale `lineTotal`); immutable issuer/recipient snapshots are built and strictly parsed; an optional company logo is resolved safely (bounded fetch, MIME/byte-signature validation, SHA-256 provenance, one no-logo retry if the primary render fails — a bad/unreachable logo never blocks Issue); an immutable PDF is rendered and structurally validated; the PDF is uploaded to a dedicated private-Storage namespace with true create-only semantics (`upsert: false` — never overwritten); then, in one short final DB transaction, the Invoice flips to `SENT` with `finalizedAt`/`pdfGeneratedAt`/`issuerSnapshot`/`recipientSnapshot`/`pdfStoragePath` all written together, a new durable `InvoicePdfArchiveObject` ledger row is promoted from `PENDING_UPLOAD` to `REFERENCED`, and the existing `STATUS_CHANGED` Activity/`INVOICE_STATUS_CHANGED` Notification fires exactly as it already did for `changeInvoiceStatusAction` — with post-commit, best-effort notification-email delivery only, never blocking the transaction.
- Concurrency: guarded by the exact same page-rendered-`updatedAt` optimistic-concurrency contract the `DRAFT` edit form already uses — a stale or already-changed invoice is rejected before any render/upload work happens.
- Failure/crash safety: the archival ledger row is written *before* the upload attempt (so a crash immediately after a successful upload still leaves discoverable evidence); any failure after a successful upload but before the final transaction commits triggers best-effort compensating cleanup of the uploaded object, never a silent orphan and never a raw provider error surfaced to the UI.
- **Now possible: retrieving the PDF, for staff or the Client Portal.** Sub-PR 3c (PR #75) added `GET /api/invoices/[id]/pdf` — any authenticated staff member (`OWNER`/`ADMIN`/`MEMBER`, no new role gate beyond org membership) can retrieve an issued invoice's archived PDF via a short-lived, per-request Supabase signed URL (307 redirect, `Cache-Control: private, no-store`, 60-second TTL, no PDF bytes proxied through Next.js). Eligibility is gated by the same `classifyInvoiceArchival()` classifier sub-PR 3a introduced — only a genuinely `archived` invoice exposes a working link; DRAFT, legacy, and any invariant-violation state return a generic 404. Before signing, the route also requires a matching `InvoicePdfArchiveObject` ledger row (all six of `organizationId`/`invoiceId`/`storagePath`/`documentVersion`/`status: REFERENCED`/`referencedAt IS NOT NULL`) whose identity independently reproduces the persisted Storage path — a missing or inconsistent ledger state fails closed to a generic 502, never attempting to sign. **PR #77 added the Portal-facing sibling route**, `GET /api/portal/invoices/[id]/pdf`, reusing this same classifier, ledger proof, and signing helper unchanged — the only differences are its `getCurrentPortalUser()` identity resolution, its own isolated `PORTAL_INVOICE_PDF_DOWNLOAD_LIMIT` rate limiter, and its Portal-scoped Invoice lookup (`clientId`/`organizationId`/`project: { clientId }`, deliberately never `project.organizationId`, which is nullable). Nonexistent, cross-org, same-org-different-client, `DRAFT`, `legacy_eligible`, and invariant-violation states all collapse to the same generic 404 on the Portal route as they do on the staff route; ledger/signing failures collapse to the same generic 502. No public/unauthenticated PDF URL exists anywhere. **Both routes are reused completely unchanged for a Legacy-Archived invoice too (PR #79, below)** — once archived, the row simply reads as `archived` to `classifyInvoiceArchival()`, exactly like an Issue-archived one. - No `InvoiceEmailAttempt` writer and no Send/email operation were added by 3b, 3c, PR #77, PR #79, or PR #82/PR #83 — that shipped later, as official Slice 4 (sub-PR 4a/PR #85, sub-PR 4b/PR #86), and has since been verified working end to end in production; see the "Invoice System Official Slice 4" subsection in Part 2. **Legacy Archive (retroactive archival for an existing eligible non-DRAFT invoice, PR #79, official Slice 3 in progress):**
- Purpose: retroactively creates the immutable snapshot/PDF archive for an existing `legacy_eligible` non-DRAFT invoice that predates the live Issue pipeline. **It does not recreate historical truth** — the confirmation UI explicitly discloses that the archive uses the invoice's *current* persisted details, which may differ from what was on file when it was originally issued.
- Entry point: a dedicated Server Action, `archiveLegacyInvoiceAction`, surfaced on the staff invoice read-only/edit page as an **"Archive Legacy Invoice"** control, behind an explicit confirmation dialog. On success, the control disappears and the existing "Download PDF" link appears in its place — the two are never rendered simultaneously (a row can never be both `archived` and `legacy_eligible` at once).
- Authorization: **OWNER-only**, enforced independently at both the Server Action boundary and the service boundary (`archiveLegacyInvoice()` in `src/lib/invoices/pdf/legacy-archive-invoice.ts`), mirroring Issue's own two-layer `assertCanAccessPaymentDetails()` discipline exactly. ADMIN and MEMBER cannot invoke it. A Portal identity cannot invoke the staff action at all — `getCurrentMembership()` redirects a Portal-only session to `/portal` before the action's own body can resolve an actor. This is not available to every staff role — only the *resulting* PDF download remains available to any staff role/the connected Portal user, per the already-shipped staff/Portal route contracts above.
- Eligibility: `classifyInvoiceArchival()` is the sole gate, never `createdAt` or an inferred historical date. `legacy_eligible` (any of `SENT`/`PAID`/`OVERDUE`/`CANCELLED` with all five archive fields null) proceeds; `DRAFT` fails as not eligible; an already-`archived` row returns an idempotent `ALREADY_ARCHIVED` success/no-op — no new render, ledger row, Storage object, or Activity; `invariant_violation` fails closed.
- Financial preservation: totals are recalculated from persisted authoritative primitives before archiving. The calculated total must exactly equal the persisted `Invoice.amount`; any existing non-null `subtotal`/`discountAmount`/`taxAmount` must exactly equal the calculated value — a mismatch fails as `INVALID_FINANCIAL_STATE` with no archive write. A null `subtotal`/`discountAmount`/`taxAmount` may be filled only after the entire row passes validation. Legacy Archive never rewrites `status`, `amount`, `paidAt`, `issueDate`, `dueDate`, `invoiceNumber`, `currency`, `documentVersion`, line items, tenant/client/project identity, or `notes`/`internalNotes`. Allowed Invoice writes are limited to `finalizedAt`, `pdfGeneratedAt`, `pdfStoragePath`, `issuerSnapshot`, `recipientSnapshot`, `updatedAt`, and the conditional null-fill of `subtotal`/`discountAmount`/`taxAmount`.
- Snapshot/PDF: built from current persisted `OrganizationProfile`/`OrganizationPaymentDetails`/`Client` data (no historical snapshot exists for a pre-feature row) via the same unchanged rendering/snapshot primitives Issue uses. `finalizedAt`/`pdfGeneratedAt` are archive-*commit* time, never a fabricated historical finalization timestamp. The persisted `documentVersion` is used and preserved exactly. The PDF is stored in the existing immutable private archive namespace, and staff/the connected Client Portal user retrieve it through the already-shipped signed-URL routes — no PDF bytes streamed/proxied through Next.js.
- Guarded commit: the final Invoice update requires the exact original status used to render, the exact `expectedUpdatedAt`, `finalizedAt`/`pdfGeneratedAt`/`pdfStoragePath` all SQL-null, and `issuerSnapshot`/`recipientSnapshot` both `Prisma.DbNull`. A zero-row guarded update produces `CONFLICT`. The ledger is registered `PENDING_UPLOAD` before Storage upload and promoted to `REFERENCED` only inside the successful final transaction.
- Activity: exactly one `UPDATED` event with `metadata.changedFields: ["legacyArchive"]` (display label "legacy PDF archive") — never `STATUS_CHANGED`, and no Notification fan-out, `InvoiceEmailAttempt`, or `PortalDownloadRequest`.
- Shared compensation: PR #79 extracted Issue's own former private compensation algorithm into `src/lib/invoices/pdf/archive-compensation.ts`; both Issue and Legacy Archive now call the same `compensateArchiveUpload()` helper (`IssueInvoiceDeps` and existing Issue behavior unchanged). Full model: **A** removal succeeds + ledger transition succeeds → `CLEANED`, object absent; **B** removal succeeds + ledger transition fails → `PENDING_UPLOAD`, object absent; **C** removal fails + ledger transition succeeds → `CLEANUP_PENDING`, object present; **D** removal fails + ledger transition fails → `PENDING_UPLOAD`, object present; **E** a crash after upload but before the final transaction → `PENDING_UPLOAD`, object present, compensation never attempted; a thrown removal is normalized to the bounded `remove_failed` category; no raw provider/database exception is ever persisted or exposed. **A `PENDING_UPLOAD` ledger row alone cannot distinguish state B from state D/E** — a bounded reconciliation mechanism must compare actual Storage state against ledger/reference state using its own safety-window/locking contract to tell these apart; PR #79 did not implement that mechanism — **PR #82 later did, see the "Bounded archival reconciliation/cleanup" subsection below.**
- Concurrency: two simultaneous archive attempts on the same invoice produce exactly one winning `REFERENCED` archive, one successful Invoice commit, one `UPDATED` Activity, and the loser's own ledger/object compensated/cleaned.
- Schema/migration: PR #79 reused the existing `InvoicePdfArchiveObject` schema/status machine — no new Prisma model, enum, or migration.

**Bounded archival reconciliation/cleanup (implemented PR #82, activated PR #83, completing official Slice 3):**
- Purpose: resolves an `InvoicePdfArchiveObject` row left in `PENDING_UPLOAD` or `CLEANUP_PENDING` because a producer (Issue or Legacy Archive) crashed mid-operation or its own best-effort compensating removal itself failed — the exact residual case both producers' own compensation models above disclose as unresolved without a separate mechanism.
- Eligibility: a `PENDING_UPLOAD` row must be older than a 30-minute safety window (`SAFETY_WINDOW_MS`) before it is ever a candidate — chosen to structurally exceed the documented maximum Vercel Function invocation lifetime, so the one production invocation that could still be genuinely finalizing that exact row is guaranteed to have already terminated. A `CLEANUP_PENDING` row (an earlier compensating removal that failed) has no age requirement. Either status is capped at 20 cleanup attempts (`MAX_CLEANUP_ATTEMPTS`) before it stops being auto-retried and surfaces instead as a `manualReviewPending` diagnostic count, requiring direct operator resolution.
- Claim protocol: each invocation generates one fresh, cryptographically-random claim token; a row is claimed via an atomic `UPDATE` that re-proves the full eligibility predicate (closing the gap between an earlier `SELECT` and this claim), and every guarded release write later in the same run requires `id` + that exact claim token + a `PENDING_UPLOAD`/`CLEANUP_PENDING` status restriction — never `cleanupLockedAt` equality alone. A claim older than 10 minutes (`CLEANUP_LEASE_MS`) is treated as abandoned by a crashed worker invocation and reclaimed by a later run.
- Per-row outcome: an indexed Invoice-reference check first (never re-claims a row a live producer has since finalized); a canonical-path parse/round-trip proof recovering the archive identity from the row's own immutable `storagePath` (since `invoiceId` may already be `NULL` after a source DRAFT's deletion); a Storage existence probe (`probeInvoicePdfObject()` — only a confirmed HTTP 404 means confirmed absence; anything else fails closed); absent → released `CLEANED`; present → a second reference re-check, then `removeInvoicePdfObject()`, then released `CLEANED` on success or `CLEANUP_PENDING` (retry later) on a bounded `remove_failed`. Only a fixed, bounded failure category is ever persisted to `lastCleanupFailureCategory` — never a raw Storage/database error, path, or signed URL.
- Producer coordination: both `issue-invoice.ts` and `legacy-archive-invoice.ts` gained a pre-upload ownership recheck immediately before calling `deps.upload` — defense in depth against a producer that stalled between creating its `PENDING_UPLOAD` ledger row and actually uploading, during which the reconciliation worker could have claimed (or already reconciled) that exact row. A rejected/thrown recheck (the approved correction head's own fix) returns the same bounded producer failure code the pre-existing null-result branch already used — `deps.upload` is never called on either branch, and no compensation is needed since no upload was ever attempted.
- Compensation coordination: both `archive-compensation.ts` `updateMany` branches now additionally require `cleanupLockedAt: null`/`cleanupClaimToken: null` — a producer's own best-effort compensating removal can never silently overwrite a row the reconciliation worker currently holds claimed.
- Batch bound: both the real worker and its dry-run sibling are capped at 25 rows per invocation (`BATCH_SIZE`), enforced through one shared `resolveBatchSize()` resolver (added in the approved correction head) that rejects any out-of-range value with a `RangeError` before either worker makes any Prisma/Storage call — never a silent clamp, which would hide a programmer error in a future internal caller instead of surfacing it.
- Routes: `GET /api/cron/invoice-pdf-reconciliation` (the real, write-capable worker) and `GET /api/cron/invoice-pdf-reconciliation/dry-run` (a true zero-write preview — same eligibility predicate, same probe, but never claims, never releases, never calls `removeInvoicePdfObject()`) — both `CRON_SECRET`-protected by the same shared `requireCronAuth()` helper every other cron route uses, both declaring a literal `maxDuration = 60`.
- Activation: PR #82 shipped both routes **dormant** — no schedule, so neither could ever fire in production on its own. PR #83 later added exactly one third `vercel.json` cron entry, scheduling only the real route once daily at `0 7 * * *` UTC — the dry-run route remains permanently unscheduled by design, existing solely for manual, authorized, pre-activation verification. **Invoice email (Send/Resend/Issue & Send, sub-PR 4a/PR #85 + sub-PR 4b/PR #86, completing official Slice 4, corrected by PR #87):**
- Purpose: emails an already-issued invoice's archived PDF to its `Client`, or — for a still-`DRAFT` invoice — Issues it first (the exact same Slice 3 Issue/archive service, never a separate finalization path) and only then sends, in one combined action.
- Authorization: **OWNER-only**, re-derived independently at both the Server Action (`sendInvoiceEmailAction`, `src/app/(dashboard)/invoices/[id]/edit/send-email-actions.ts`) and service (`sendInvoiceEmail()`, `src/lib/invoices/email/send-invoice-email.ts`) layers — the same two-layer `assertCanAccessPaymentDetails()` discipline Issue and Legacy Archive already use. Rate-limited (`INVOICE_EMAIL_SEND_LIMIT`); every query is `organizationId`-scoped.
- Recipient: always the scoped `Client.email`, read fresh server-side and validated at send time, snapshotted per-attempt into `InvoiceEmailAttempt.recipientEmail` — never client-submitted. A missing or invalid Client email blocks send with a clear, actionable error before any provider call.
- Attachment: the already-archived, immutable PDF — never regenerated for the email — downloaded via the storage layer's existing signed identity/path helpers. A "View invoice" Portal link is included in the email body only if the Client has active Portal access; never a gate on whether the email can be sent at all, and never an unauthenticated access token.
- Idempotency/concurrency: every Send/Resend click carries a fresh UUIDv4 `idempotencyKey`, unique-constrained in the database, so a retried request reconciles against the existing row instead of duplicating; the partial unique Postgres index (`invoice_email_attempt_one_pending`, migration `20260914090000_add_invoice_email_attempt_pending_index`, `WHERE status = 'PENDING'`) is the hard, database-enforced backstop against two concurrent active sends for the same invoice.
- Settlement states: `PENDING → ACCEPTED | FAILED | UNKNOWN` — `ACCEPTED` means the provider accepted the request (not proof of inbox delivery); `FAILED` means a confident pre-acceptance rejection (provider error, or the app's own `EMAIL_NOT_CONFIGURED`/no-or-invalid-recipient checks); `UNKNOWN` means the outcome couldn't be established (a crash/timeout mid-call, or a network error) and is never silently reclassified as `FAILED`. A `PENDING` row older than 120 seconds is swept to `UNKNOWN` on the next request touching that invoice, never auto-converted to `FAILED`. Resending after an `UNKNOWN` attempt requires an explicit staff acknowledgement of that exact attempt's id and always uses a brand-new `idempotencyKey`.
- UI (`InvoiceSendControls`): one context-dependent control — "Issue & Send" for a still-`DRAFT` invoice, "Send invoice" for an issued invoice with no prior `ACCEPTED` attempt, "Resend invoice" once one exists — plus a bounded, newest-first "Email attempts" history list (`loadInvoiceEmailAttempts()`, OWNER-only, tenant-scoped, capped at 20 rows).
- Security/logging: no raw provider error, recipient address, or PDF/base64 content is ever logged — only fixed, bounded failure categories. No `PortalDownloadRequest` row is ever written by this feature (that Portal Analytics metric remains scoped to Attachment downloads only, unchanged).
- **Button-visibility correction (PR #87):** a reproduced production defect — the Issue invoice/Issue & Send buttons rendered as invisible white-on-white text — was root-caused to the shared `Button` component's hardcoded base color classes conflicting with a caller-appended raw override className at equal Tailwind specificity, and fixed with a mutually-exclusive `variant` prop. The same PR's second commit closed the identical latent risk on three more call sites found by an audit of every `Button` usage in the app (`InvoiceForm`'s "Add line" button, `InvoiceLegacyArchiveControls`, and `InvoiceLifecycleControls`'s transition/Cancel buttons).
- **Production verification:** the PR #86 migration was deployed and confirmed applied; the exact PR #86 and PR #87 merge commits were confirmed deployed to production; a real QA Invoice was issued exactly once through the normal UI and its archived PDF verified; the first live Send request was correctly rejected (`EMAIL_NOT_CONFIGURED`, no `InvoiceEmailAttempt` row created) because the production `RESEND_API_KEY` was absent — found via a read-only environment-variable metadata audit, never a value access; the key was then added to Production and the sender variable updated, the same commit redeployed, and exactly one newly authorized Send request settled `ACCEPTED`, with exactly one attempt persisting after a hard reload and exactly one email reaching a controlled test mailbox with a correct PDF attachment. See Part 2's "Invoice System Official Slice 4" and "Production deployment and first live Invoice-email verification" subsections for the complete chronology. **Operational limitation:** this verification used Resend's own testing-domain sender — real-customer rollout still requires a separately verified custom sending domain and Production sender address; this is a deployment prerequisite, not a code defect, and does not reopen Slice 4's implementation.
- Schema/migration: `InvoiceEmailAttempt` itself was schema-reserved since Slice 1 (PR #65); sub-PR 4b added exactly one new migration, the partial unique PENDING index above — no new model, enum, or column.
- **With this, official Invoice System Slice 4 has no remaining piece.**

**Duplicate-as-new-DRAFT (`CANCELLED`-only, PR #70, completing official Slice 2):**
- Eligibility is exact: only an authorized, organization-scoped, exactly-`CANCELLED` invoice exposes the "Duplicate as new draft" link (`InvoiceLifecycleControls`, the read-only view) and resolves the dedicated route, `/invoices/[id]/duplicate`. `DRAFT`, `SENT`, `PAID`, `OVERDUE`, a cross-organization id, and a nonexistent id all resolve through the same `notFound()` — structurally indistinguishable.
- The source loader (`src/lib/invoices/duplicate-source.ts`, `getDuplicateSourceInvoice()`) uses an explicit, minimal Prisma `select` — never `include` — and its result type is inferred from that `select` via `Prisma.InvoiceGetPayload`, so the query and its type can never drift apart. **Opening the page performs zero writes.**
- The invoice-number suggestion is exactly `` `${original.trim()}-R1` `` (`suggestDuplicateInvoiceNumber()`, `src/lib/invoices/duplicate.ts`) — no existing `-R<n>` suffix is detected/incremented, no database lookup, no reservation, and it is **never auto-submitted**: staff must explicitly review, optionally edit, and submit.
- Source `currency` is canonicalized (`trim().toUpperCase()`) once, at the page boundary. A supported canonical currency is copied unchanged into the new draft as its actual denomination. An authorized `CANCELLED` source whose currency is **unsupported** renders a disclosed 200 blocked state instead — no `InvoiceForm`, no submit control, no silent USD substitution.
- The pure mapper (`buildDuplicateInvoiceDefaults(source, today)`) takes an **injected** `today` — never an internal `new Date()`. A flat source copies `amount`; an itemized source copies ordered `description`/`quantity`/`unitPrice` per line and sets `amount: ""` (never a dormant copy of the source's own aggregate total). `issueDate` always resets to `today`; `dueDate` and `internalNotes` always reset blank; `notes` and every discount/tax input are copied unchanged.
- Submission goes through the **ordinary, unmodified `createInvoiceAction`** — the exact same action `/invoices/new` uses. No `sourceInvoiceId` or any other source-identity value is ever added to the submitted form. **The created invoice is an ordinary new `Invoice` row — Duplicate creates no database relation to its source.** Project ownership is reverified server-side; `clientId`/`organizationId` are re-derived from the verified Project; every total and every line-item `lineTotal` is recomputed server-side; every line-item `id`/`position` is freshly assigned. The new invoice is always `DRAFT` with `paidAt: null`.
- The source invoice itself — and its own Activity history — are left completely unchanged by opening the page or by a successful duplicate submission. No attachments, `InvoiceEmailAttempt` rows, finalization fields, snapshots, or PDF state are ever copied from source to duplicate. A successful duplicate produces exactly one ordinary `INVOICE`/`CREATED` Activity row for the *new* invoice, identical in shape to any other invoice creation — nothing references the source id.
- No schema, migration, dependency, lockfile, Portal, Paddle, or architecture-doc change was made to ship this.

**Compatibility, unchanged:**
- `amount` remains the sole canonical total every Dashboard/Analytics/Search/Portal read consumes.
- A flat invoice is still exactly `lineItems.length === 0` — no new discriminator column, no fabricated row ever created for a flat invoice.
- `organizationId` remains the required, schema-enforced (`NOT NULL`) primary tenant predicate on every Invoice query (`project.organizationId` retained as defense-in-depth) — unchanged since PR #63.
- The invoice-numbering uniqueness constraint was `@@unique([clientId, invoiceNumber])` at the time of Slice 2a/2b and PR #70 (unchanged by any of them) — the target, organization-wide `[organizationId, invoiceNumber]` constraint (`docs/invoicing-architecture.md` §4.5) was implemented later, by official Slice 5c (PR #91), and is now the live constraint.

## PART 12 — Client Portal (major differentiator)

This is one of the most fully-built and structurally deliberate features in the codebase.

**How a client gets access:** a staff member, from a Client's detail page, invites them by email (`ClientInvitation`, token-based, expiring). The client receives an email (Resend, with a copyable-link fallback), visits `/portal/invite/[token]`, and completes signup — this creates a `PortalUser` row whose `id` equals their new Supabase Auth user id.

**Authentication:** entirely separate pages/actions from staff auth (`/portal/login`, `/portal/signup`, `/portal/forgot-password`, `/portal/reset-password`), resolved via `src/lib/current-portal-user.ts`, never via the staff `getOrCreateUser()`/`getCurrentUserOrganization()` path. A `PortalUser` is never given a `Membership` and is never resolvable as a staff identity.

**Portal routes** (`src/app/portal/(app)/`): Overview (`page.tsx`), Projects (list + detail), Invoices (list + detail), Profile. Navigation is a distinct shell with its own "CLIENT PORTAL / <client name>" header — visually and structurally separate from the staff app.

**What a portal user can see:** only Projects and Invoices belonging to the one `Client` record they're attached to, plus that Client's Attachments (read-only, on the relevant project/invoice/client). **Zero access** to other clients, staff data, team management, billing, or analytics — enforced by `resolvePortalIdentity()` deriving `organizationId`/`clientId` purely from the `PortalUser` → `Client` relation, never from any client-supplied value.

**Messages:** there is **no portal-facing messaging/chat feature** — the only "communication" surface is the staff-only Comments system on Projects/Tasks (Part 13), which a Portal identity cannot see or use at all.

**Files:** portal users see read-only Attachments already uploaded by staff; there is no portal-side upload capability.

**Isolation:** verified both by direct code reading (`resolvePortalIdentity`) and by the E2E test suite (`staff-app.spec.ts`, portal-specific specs) and the dedicated `check-portal-welcome-security.mjs` static check.

## PART 14 — Files / Storage

`src/lib/storage/` + `src/app/api/attachments/[id]/download/route.ts` + `src/app/api/portal/attachments/[id]/download/route.ts`.

- Two Supabase Storage buckets: a **private** `attachments` bucket (Client/Project/Invoice files — the schema also reserves `AttachmentEntityType` room but Task attachments are not currently wired into any UI) and a **public** `logos` bucket (organization branding).
- Uploads: server-validated type/size allowlist (`src/lib/storage/attachments-config.ts`), a fresh server-generated `storagePath` (never derived from user input), metadata (`originalName`, `mimeType`, `sizeBytes`) stored in the `Attachment` row.
- Downloads: authenticated Route Handlers issue short-lived signed Storage URLs and return 307 redirects to them — they never expose a permanent public URL for the private bucket, and never stream/proxy the file bytes through Next.js (verified directly against both route handlers' source). The staff route (`/api/attachments/[id]/download`) scopes access by organization membership; the Client Portal has its own parallel download route (`/api/portal/attachments/[id]/download`) that additionally enforces Client-scoped portal attachment access, and records a `PortalDownloadRequest` row only after authorization and successful signed-URL generation (Phase 22/PR #60).
- Deletion: an Attachment delete removes both the DB row and the Storage object; deleting a parent Client/Project/Invoice cascades to delete its Attachments and their Storage objects (a dedicated cleanup pass, not an automatic DB-level cascade, since `entityId` is intentionally not a foreign key).
- UI: an `attachments-section.tsx` component pattern shared across Clients/Projects/Invoices, plus a read-only portal-side variant.

## PART 15 — Notifications

`Notification`/`NotificationDelivery`/`NotificationPreference` models, `src/lib/notifications/`.

- **Triggers:** a curated subset of Activity events (role changes, ownership transfer, member removal, staff/portal invitation acceptance, invoice status changes, comment @-mentions) plus billing-webhook-driven events (subscription activated/canceled, payment failed, plan changed) written directly by `src/lib/billing/notify.ts` — most routine Activity volume (ordinary create/update on Clients/Projects/Tasks, every Attachment event) is deliberately never notified.

- **Links/actions:** each notification's metadata carries enough structured data (never a pre-rendered string, never a token) for a formatter to render display text and a link to the relevant entity at read time.

## PART 19 — Security Work Already Implemented

**Implemented:**
- Server-side session verification on every protected page/action (`getVerifiedAuthUser()`), never trusting a client-supplied identity.
- `organizationId` scoping enforced in every business-entity query, resolved server-side from a verified `Membership`, never from client input.
- Role checks re-verified inside Server Actions (not just hidden in the UI) for sensitive mutations (team, billing, payment details).
- Supabase's auto-generated Data API is **fully locked down** — anon/authenticated Postgres privileges were explicitly revoked on all public-schema tables (migration `20260802120937_lockdown_public_schema_grants`), meaning the app deliberately does **not** rely on Postgres Row-Level Security policies for authorization — all authorization is application-layer, enforced through Prisma using a privileged server-side connection, with the Data API itself made inert as defense-in-depth. A dedicated check (`check-no-data-api-access.mjs`) guards this.
- Hardened Supabase Auth session cookie flags (httpOnly/secure/sameSite).
- Centralized rate limiting on auth, invitation, attachment, and billing-checkout/portal endpoints.
- Production-grade HTTP security headers.
- `sanitizeRedirectPath()` used everywhere a `redirectTo` value could otherwise enable an open redirect.
- Paddle webhook signature verification + idempotent processing (`WebhookEvent.providerEventId` unique constraint) — no unauthenticated write path into billing state.
- **15 dedicated, CI-enforced static security/invariant checks currently exist** (`scripts/security-checks/`, run via `npm run security:check`) — the current suite passes 15/15 (the original-investigation value of 14/14 remains preserved only in Part 21's explicitly historical baseline table/provenance, not restated here). They check things like: Platform Admin is never reachable from tenant code and never uses raw SQL; the Portal welcome banner can never leak org/user identifiers or write Activity/Notification rows; the search backend never touches Client Portal data and never console-logs; no raw SQL queries anywhere; no `dangerouslySetInnerHTML`; no secrets in public/client bundles; `TEST_MODE` bypass code can't leak into a real deployment path.
- A comprehensive automated test suite — **3,374 tests, current baseline as of PR #92** (unit 2,142 + integration 905 + E2E 327 = 3,374; historical totals recorded at earlier points, e.g. 3,308 as of PR #87, remain accurate descriptions of that earlier moment — see Part 21) including dedicated authorization/tenant-isolation integration tests (`test/integration/authorization/`, `test/integration/security/`) and E2E security-UI specs (redirect-safety, XSS-as-literal-text rendering).

**Known security-relevant gaps (disclosed, not hidden):**
- Rate limiting is **in-memory, per-instance** — not effective across multiple concurrent server instances in a horizontally-scaled deployment.
- No public OSS license file exists for the original application code (a legal/IP disclosure, not a code-security issue).
- Custom-domain DNS ownership is never actually verified (see Part 24) — a cosmetic/trust gap, not an access-control one, since the app's own tenant resolution never depends on the request's Host header.

## PART 27 — Context the Next Assistant Must Preserve

**Preserve, don't rebuild:**
- The multi-tenant data model (`Organization`/`Membership`/`organizationId` scoping) — this was a deliberate, carefully-executed retrofit (Phase 1) that every subsequent feature was built on top of. Re-deriving it from scratch would be a massive regression.
- The staff (`User`) vs. Client Portal (`PortalUser`) identity separation — this is intentional and structural, not accidental duplication. Never merge these into one table or one auth code path; the schema comments explicitly explain why they're kept apart.
- The Server Components + Server Actions architecture — there is no REST/GraphQL API layer for the app's own UI, and none should be introduced without a strong reason; this is a deliberate, consistent choice throughout, not an oversight.
- The hand-rolled `FormData` validation pattern (`src/lib/validation/*.ts`) — consistent across the whole app; introducing a schema library (e.g. Zod) partway through would fragment the codebase's own conventions.
- The append-only Activity log + Notification fan-out pattern — both are single-choke-point designs (`createActivity()`, `dispatchNotificationsForActivity()`) specifically so future features plug into one place rather than scattering logging/notification logic everywhere.
- The Data-API-lockdown security model — authorization is enforced entirely in application code (Prisma + server-verified session), *not* via Postgres RLS policies, which are deliberately made inert. Do not assume RLS policies exist or would do anything if a table's grants were restored — that would silently reopen the tenant boundary the "no RLS" security check exists to prevent.
- The provider-neutral billing adapter pattern (`src/lib/billing/provider/provider.ts`) — the real Paddle adapter, the mock, and an "unconfigured" stub are resolved through one interface; a future second provider should follow the same shape.
- The 15 `scripts/security-checks/` static checks and the 3,130-test suite — treat a red result here as a real regression signal, and extend this pattern (a new invariant gets a new check) rather than inventing a different verification mechanism.
- **The bounded archival reconciliation/cleanup claim protocol (PR #82/#83)** — the claim-token-only ownership proof (never `cleanupLockedAt` equality alone), the `SAFETY_WINDOW_MS`/`MAX_VERCEL_FUNCTION_DURATION_MS`/`CLEANUP_LEASE_MS` module-load assertions, and the shared `resolveBatchSize()` hard ceiling are all deliberate, narrow invariants — do not weaken any of them, and do not schedule the `/dry-run` sibling route, which exists solely for manual pre-activation verification.
- **The Portal Analytics privacy boundary (Phase 22/PR #60–#61)** — new, narrow, and easy to accidentally widen:
  - `PortalUser.lastLoginAt` remains a single mutable current-state timestamp; do not turn it into per-login history without a separate privacy/design review.
  - `PortalDownloadRequest` must remain organization-only and must not acquire `portalUserId`, `attachmentId`, `clientId`, PII, or URL/storage/auth/session metadata without explicit review — `check-analytics-security.mjs` check #13 enforces this as an exact field allowlist, not a keyword ban.
  - The two new Portal metric queries (`getPortalEngagementCounts()`) use literal selected `TimeRange` bounds; do not route them through `growthBounds`/`DEFAULT_GROWTH_TIME_RANGE` the way growth-comparison metrics are.
  - The two new cards ("Recently active portal users," "Download-link requests") are intentionally plain scalars, not `GrowthMetric`/chart data — don't add a trend chart or previous-period comparison without re-deriving whether the underlying data can honestly support one (`lastLoginAt` currently cannot).

**Dangerous to change without understanding first:**
- `getCurrentUserOrganization()`/`getCurrentMembership()`/`getCurrentPortalUser()` — the entire authorization boundary funnels through these few functions. Any change here has tenant-isolation blast radius.
- The Supabase Data API grants migration (`20260802120937_lockdown_public_schema_grants`) — restoring public-schema grants without re-adding equivalent RLS policies would reopen a real security hole, since the app currently assumes the Data API is inert.
- `entityId` fields that are deliberately *not* foreign keys (Activity, Notification, Attachment, Comment) — this is intentional (so history survives deletion of the thing it describes), not a modeling mistake; "fixing" it into a real FK would break the audit-log philosophy those models were built around.
- The `active_organization_id` cookie — it is explicitly documented as a UX preference only, never an authorization decision; every read re-verifies a live Membership. Don't start trusting it directly.

**Conventions to follow:**
- One `docs/<feature>-architecture.md` design doc per major feature (Analytics, Billing, Comments, Notifications, Onboarding, Search) — written *before* implementation, in past phases; continuing that habit for new major features would match the project's own established practice.
- PR-per-feature-slice development with a merged branch cleaned up afterward — consistently followed (the two branches that briefly sat unmerged were investigated and resolved via PR #58; see Part 2's Phase 21 and Part 24).
- Every new capability gets real automated test coverage across the same three tiers (unit/integration/E2E) this project already uses, not just manual verification.
